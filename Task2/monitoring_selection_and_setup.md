# Выбор и настройка мониторинга в системе

## 1. Анализ системы в контексте мониторинга

Сейчас единственный источник данных о работе системы — Яндекс Метрика на сайте онлайн-магазина. Она видит только поведение B2C-покупателей в браузере. Всё, что происходит дальше, для неё невидимо:
- B2B-заказы через API MES;
- обмен сообщениями между CRM и MES;
- расчёт стоимости;
- работа продавцов и операторов;
- состояние серверов и баз данных.

Что нужно наблюдать по C4-диаграмме:

| Часть системы | Тип | Чем важна для мониторинга |
|---|---|---|
| Shop API | Spring Boot, 1 инстанс | Вход B2C-заказов, приём 3D-файлов. |
| CRM API | Spring Boot, 1 инстанс | Подтверждение заказов продавцами. Пишет в чужую Shop DB. Публикует и получает события через RabbitMQ. |
| MES API | C#, 1 инстанс | Самая нагруженная часть: дашборд операторов, публичный B2B API, тяжёлый расчёт стоимости (2–30 мин). Главный кандидат на перегрузку. |
| RabbitMQ | брокер | Единственный канал между CRM и MES. Для B2B заказ в CRM появляется только из сообщения. Потеря или застревание сообщения — это потеря заказа. |
| Shop DB, MES DB | Managed PostgreSQL, по 1 инстансу | Shop DB делят Shop API и CRM API. MES DB обслуживает и запись, и тяжёлое чтение дашборда. |
| 3D files storage | S3 | Растёт с каждым заказом, нужен для расчёта. |
| Фронтенды (Internet Shop, CRM, MES) | SPA | Пользовательское время загрузки. Для магазина его частично даёт Яндекс Метрика. |
| Жизненный цикл заказа | бизнес-процесс поверх трёх систем | Статус «размазан» по Shop DB, MES DB и сообщениям. Техническими метриками этого не увидеть, нужны бизнес-метрики. |

## 2. Мотивация

**Проблема бизнеса.** Компания теряет крупные B2B-контракты и лояльность B2C-клиентов из-за просроченных и «потерянных» заказов. Операторы жалуются на медленный MES. При этом:

- **Мы узнаём о проблемах от клиентов**, причём через недели, когда заказ уже просрочен. Восстановить, что произошло, почти невозможно.
- **Мы не видим B2B-канал.** Яндекс Метрика его не покрывает, а именно после открытия API жалоб стало больше. Неизвестно, сколько заказов приходит через API, сколько из них зависает и где.
- **Мы не знаем, почему тормозит MES.** Фильтр и пагинация не помогли, а следующие шаги команда выбирает вслепую. Возможно, дело в расчётах, в базе, в нехватке памяти. Без данных каждое такое исправление — это спринт работы с непредсказуемым результатом.
- **Мы не можем планировать ёмкость.** Нагрузка растёт на 100 заказов в месяц. Неизвестно, когда упрёмся в CPU, диски или соединения БД, поэтому узнаем об этом в момент аварии.

**Что даст мониторинг:**

| Эффект | Как измерим |
|---|---|
| Проблемы с заказами обнаруживаются за минуты или часы, а не за недели. Поддержка связывается с клиентом раньше, чем он пожалуется. | Время от появления проблемы до её обнаружения (MTTD). Доля инцидентов, обнаруженных мониторингом, а не клиентом. |
| Сокращается число просроченных заказов: зависший заказ виден, пока ещё можно уложиться в срок. | Число заказов, превысивших норму времени в статусе. Доля заказов, выполненных за обещанные три недели. |
| Решения о доработках и масштабировании принимаются по данным. Деньги и время команды тратятся на настоящие узкие места. | Эффект каждой доработки виден на графиках «до/после». |
| Можно давать B2B-партнёрам измеримые обещания (SLA) и подтверждать их выполнение. | Доступность и время ответа B2B API, время расчёта стоимости. |
| Безопаснее релизы: ухудшение после деплоя видно сразу. | Рост ошибок и времени ответа после релиза. |

**Стоимость.** Используем open-source инструменты (Prometheus, Grafana) или управляемые сервисы Yandex Cloud. Лицензии не нужны, основные затраты — время команды и небольшие ВМ. Это дешевле одного потерянного крупного контракта.

## 3. Выбор подхода к мониторингу

Разные части системы устроены по-разному, поэтому подходы комбинируются:

| Часть системы | Подход | Почему |
|---|---|---|
| **Shop API, CRM API** | **RED** (Rate, Errors, Duration) | Это сервисы, которые обрабатывают запросы. Для них важно, сколько запросов приходит, сколько завершается ошибкой и как долго они выполняются. |
| **MES API** (включая B2B API) | **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) | Тоже сервис запросов, но с тяжёлой фоновой нагрузкой: расчёты конкурируют с дашбордом операторов и запросами партнёров. Одного RED мало, нужна ещё **насыщенность**: загрузка CPU и памяти, очередь расчётов, число одновременных расчётов. Именно насыщенность — вероятная причина жалоб операторов. Кроме того, это внешний API с потенциальным SLA перед партнёрами. |
| **Инфраструктура:** ВМ, Shop DB, MES DB, RabbitMQ, S3 | **USE** (Utilization, Saturation, Errors) | Это ресурсы, а не обработчики запросов. Для них важно, насколько они заняты, есть ли очередь и есть ли сбои. RabbitMQ тоже рассматриваем как ресурс: очереди, сообщения в обработке, «мёртвые» письма. |
| **Жизненный цикл заказа** | **Бизнес-метрики** (дополнительно к трём подходам) | Ни RED, ни USE не покажут, что заказ две недели стоит в `MANUFACTURING_APPROVED`. Технически всё может быть «зелёным», а заказ при этом потерян. Это главная боль бизнеса, поэтому заводим отдельные метрики по статусам. |

**Общие ярлыки для всех метрик:** `env` (dev, release, prod), `service` и `instance`.

**Правило по ярлыкам.** В ярлыки не попадают значения с неограниченным числом вариантов: `order_id`, `user_id`, полный URL, текст ошибки. Каждое уникальное значение ярлыка создаёт отдельный временной ряд, и хранилище метрик «распухает». Конкретные заказы и пользователи — задача логов и трейсинга. Для HTTP используем шаблон маршрута (`/orders/{id}`), а не фактический путь.

## 4. Метрики

### 4.1. Метрики из предложенного списка, которые отслеживаем

#### RabbitMQ (USE)

| № | Метрика | Зачем | Ярлыки |
|---|---|---|---|
| 1 | Number of dead-letter-exchange letters in RabbitMQ | Каждое «мёртвое» письмо — сообщение о заказе, которое не удалось обработать, то есть потенциально потерянный заказ. Самый прямой сигнал проблемы, на которую жалуется бизнес. Алерт на любое новое сообщение в DLQ. | `queue` — исходная очередь (по ней понятно, какой поток сломан: новые заказы, статусы, расчёты). `reason` — причина: rejected, expired, maxlen, delivery_limit. Rejected — ошибка в обработчике, expired и maxlen — получатель не успевает. |
| 2 | Number of message in flight in RabbitMQ | Рост числа сообщений в очереди или в обработке значит, что получатель не успевает или «завис». Заказы при этом формально не потеряны, но задерживаются. Показатель насыщенности брокера и получателей. | `queue`. `state`: ready (ждут получателя) и unacked (взяты, но не подтверждены). Много unacked при нуле ready — получатель «завис» на сообщениях. |

#### Количество запросов (Rate / Traffic)

| № | Метрика | Зачем | Ярлыки |
|---|---|---|---|
| 3 | RPS for internet shop API | Нагрузка B2C-канала. База для планирования ёмкости. Резкое падение до нуля — признак аварии, которого не видно по ошибкам. | `method`, `route` (шаблон маршрута), `status_class` (2xx, 4xx, 5xx). |
| 4 | RPS for CRM API | Нагрузка от продавцов. Показывает, справляется ли CRM с ростом заказов. | `method`, `route`, `status_class`. |
| 5 | RPS for MES API | Нагрузка на самую критичную часть. Нужно разделять трафик операторов и B2B-партнёров, чтобы видеть, кто создаёт нагрузку. | `method`, `route`, `status_class`, `client_type` (operator, b2b). |
| 8 | RPS per user for MES API — **в изменённом виде: по B2B-партнёру, а не по пользователю** | Один активный партнёр может перегрузить MES для всех. Метрика показывает, кто из партнёров создаёт нагрузку, и нужна для квот и ограничения запросов. По отдельным операторам метрика не нужна. | `partner_id`. Партнёров десятки, поэтому число рядов ограничено. Плюс `route`, чтобы отличать расчёты от прочих запросов. |

#### Ошибки (Errors)

| № | Метрика | Зачем | Ярлыки |
|---|---|---|---|
| 25–27 | Number of HTTP 200 for shop / CRM / MES API | Отдельной метрикой не заводим. Это часть счётчика запросов (п. 3–5) с ярлыком `status`. Нужна как знаменатель для доли ошибок: 500-х может быть 10, но важно, 10 из 100 или 10 из 100 000. | см. п. 3–5 |
| 28–30 (31 — дубль 28) | Number of HTTP 500 for shop / CRM / MES API | Ошибки сервера означают, что заказ не создан, статус не изменён или расчёт не выполнен. Алертим по **доле** 5xx от всех запросов, а не по абсолютному числу. Тоже берётся из счётчика запросов с ярлыком `status`. | `route`, `status` (500, 502, 503, 504: так отличаются ошибки кода от таймаутов). Для MES: `client_type`. |

#### Время ответа (Duration / Latency)

| № | Метрика | Зачем | Ярлыки |
|---|---|---|---|
| 19 | Latency for shop API | Медленный магазин — это брошенные корзины. Важно время загрузки 3D-файла и оформления заказа. | `method`, `route`, `status_class`. Хранится как гистограмма, смотрим перцентили p50, p95, p99. Среднее скрывает «хвост» медленных запросов. |
| 20 | Latency for CRM API | Влияет на скорость работы продавцов с подтверждением заказов. | `method`, `route`, `status_class`. |
| 21 | Latency for MES API | Прямо измеряет жалобу операторов на медленный дашборд. Позволяет проверить эффект доработок. Отдельно отслеживаем B2B-запросы, это основа SLA. | `method`, `route`, `status_class`, `client_type`. Запросы расчёта стоимости выделяем отдельным `route`, иначе их минуты исказят картину по остальным запросам. |

|---|---|---|---|

| № | Метрика | Почему не нужна |
|---|---|---|
| 6 | RPS per user for internet shop API | Покупателей тысячи, и их число растёт. Ярлык `user_id` создаст огромное число временных рядов. Поведение отдельных покупателей лучше анализировать в Яндекс Метрике и логах. Защиту от злоупотреблений лучше делать ограничением запросов на входе. |

| 38–40 | Kb sent for shop / CRM / MES API | Аналогично: объём ответов не связан с известными проблемами. При необходимости сетевой трафик ВМ доступен в стандартных метриках облака. |

### 4.3. Дополнительные метрики (нет в списке)

#### Жизненный цикл заказа — бизнес-метрики

Это главный блок для бизнеса. Именно он показывает потерянные и зависшие заказы.

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Количество созданных заказов | Входящий поток заказов. Сравнение B2C и B2B. Проверка прогноза роста (+100 в месяц). Резкое падение до нуля — авария, которую не видно по техническим метрикам. | `channel` (b2c, b2b), `partner_id` (для b2b) |
| Количество переходов между статусами | Видно, сколько заказов проходит каждый этап в единицу времени. Если заказы входят в статус, но не выходят — там затор. | `from_status`, `to_status`, `system` (shop, crm, mes) |
| Количество заказов в каждом статусе (текущее) | «Воронка» заказов: где копятся. Например, рост числа заказов в `PRICE_CALCULATED` — продавцы не успевают подтверждать. | `status`, `channel` |
| Возраст самого старого заказа в статусе | Главная метрика зависших заказов. Алерт, если превышена норма для статуса (например, `MANUFACTURING_APPROVED` дольше двух суток без `MANUFACTURING_STARTED`). Ловит в том числе «голодание» старых заказов у операторов. | `status`, `channel` |
| Время прохождения заказа от `SUBMITTED` до `SHIPPED` | Проверка обещания «три недели». Тренд показывает, становится ли лучше. | `channel` |
| Количество расхождений статусов между системами | Результат сверки статусов в Shop DB и MES DB (инициатива I3 из задания 1). Каждое расхождение — заказ, о котором системы «думают» по-разному. | `type` (нет в MES, нет в CRM, разные статусы) |

#### Расчёт стоимости (насыщенность MES)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Длительность расчёта стоимости | Расчёт — самая тяжёлая операция. Видно, как время расчёта зависит от сложности модели, и можно оценить нужную мощность. | `channel`, `complexity` (интервалы по числу полигонов: до 100 тыс., до 1 млн, больше) |
| Число расчётов, выполняемых одновременно, и число ожидающих | Прямой показатель насыщенности MES. Если ожидающих становится всё больше, MES не справляется, и заказы ждут цену. | `channel` |
| Количество неудачных расчётов | Неудачный расчёт останавливает заказ на шаге `SUBMITTED`. | `channel`, `error_type` (timeout, invalid_model, internal) |

|---|---|---|

#### API и инфраструктура

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Число одновременно обрабатываемых запросов | Насыщенность API: если число растёт, а RPS — нет, запросы «застревают». Заменяет метрики сессий (п. 32–34). | `service`, `route` |
| HTTP 4xx (в первую очередь 429 и 400 для B2B API) | 429 — партнёр упирается в лимит запросов. Рост 400 — партнёры шлют некорректные данные, нужно уведомить их или поправить документацию API. | `status`, `partner_id` |
| Доступность снаружи (внешние проверки) | Отдельная проверка доступности магазина, CRM, MES и B2B API извне. Ловит отказы, при которых сервис не может сам о себе сообщить. | `target` |

| Время выполнения медленных запросов к БД | Позволяет найти, какой запрос тормозит дашборд MES. | `db_instance`, `query_id` (ограниченный топ запросов) |

## 5. План действий

Драфт технического задания. Задачи перечислены в порядке выполнения.

**Этап 1. Платформа мониторинга**
1. Развернуть хранилище метрик (time-series база) на базе Prometheus, либо подключить Yandex Managed Service for Prometheus. Управляемый сервис снимает нагрузку с единственного DevOps-инженера.
2. Развернуть Grafana для дашбордов и Alertmanager для оповещений. Настроить вход только для сотрудников компании.
3. Описать конфигурацию мониторинга как код (Terraform, Ansible или Helm) и хранить в репозитории: дашборды и правила алертов тоже.
4. Настроить хранение: детальные данные — 30 дней, агрегированные — год (для планирования ёмкости и сравнения «до/после»).

**Этап 2. Инфраструктурные метрики (USE)**

5. Установить node_exporter на ВМ Shop API, CRM API и MES API: CPU, память, диск, сеть.
6. Включить плагин `rabbitmq_prometheus` в RabbitMQ: очереди, сообщения в обработке, DLX, получатели, память и диск узла.
7. Подключить метрики Managed PostgreSQL и Object Storage из Yandex Monitoring, а также развернуть postgres_exporter для соединений по приложениям и медленных запросов.
8. Настроить внешние проверки доступности (blackbox_exporter) для магазина, CRM, MES и B2B API.

**Этап 3. Метрики приложений (RED и золотые сигналы)**

9. Shop API и CRM API: подключить Spring Boot Actuator + Micrometer с выдачей метрик в формате Prometheus. Настроить гистограммы времени ответа и шаблоны маршрутов в ярлыках.
10. MES API: подключить сбор метрик для .NET (OpenTelemetry Metrics или prometheus-net). Добавить ярлыки `client_type` и `partner_id`. Добавить метрики расчёта стоимости: длительность, одновременные, ожидающие, неудачные.
11. Проверить, что ни одна метрика не содержит ярлыков с неограниченным числом значений.

**Этап 4. Бизнес-метрики заказов**

12. Добавить в сервисы счётчики созданных заказов и переходов статусов в момент изменения статуса.
13. Настроить периодические SQL-запросы к Shop DB и MES DB для текущих значений: число заказов в статусе, возраст самого старого заказа в статусе (через sql_exporter, на реплике или в нерабочие для БД моменты).
14. Согласовать с бизнесом нормы времени для каждого статуса. Это пороги для алертов о зависших заказах.

**Этап 5. Дашборды и оповещения**

15. Собрать дашборды:
    - «Заказы» — для бизнеса и поддержки: воронка, зависшие заказы, B2C и B2B;
    - «Сервисы» — RED и золотые сигналы по каждому API;
    - «Инфраструктура» — USE по ВМ, БД, RabbitMQ;
    - «B2B-партнёры» — нагрузка и ошибки по партнёрам.
16. Настроить правила алертов и каналы: рабочий чат, тикеты в трекере, звонок дежурному для критичных (см. раздел 6).
17. Назначить ответственных за реакцию на алерты и описать для каждого алерта, что делать (короткая инструкция).
18. Через 2–4 недели сбора данных пересмотреть пороги по фактическим значениям, чтобы убрать ложные срабатывания.

## 6. Показатели насыщенности и реакция на превышение (дополнительное задание)

**Как выбраны пороги.** Это стартовые значения. После 2–4 недель наблюдений их нужно уточнить. Логика такая:
- **Предупреждение** срабатывает, когда запас ещё есть, но пора действовать в плановом порядке. Реакция — тикет или сообщение в чат, в рабочее время.
- **Критический порог** — ресурс почти исчерпан, и пользователи вот-вот почувствуют проблему или уже чувствуют. Реакция — немедленная, с оповещением дежурного.
- **Длительность превышения** («держится N минут») отсекает кратковременные всплески, на которые реагировать не нужно.
- Для ресурсов, которые растут постепенно (диски, размер данных), используется **прогноз**: алерт, если при текущем темпе ресурс закончится через N дней. Нагрузка растёт линейно, поэтому прогноз надёжен.

| Показатель насыщенности | Предупреждение | Критично | Почему такой порог | Что происходит |
|---|---|---|---|---|
| **CPU MES API** | > 75% в течение 15 мин | > 90% в течение 5 мин | Выше ~80% растёт время ответа: расчёты и запросы операторов начинают ждать процессор. У MES один инстанс, запаса нет. | Предупреждение: тикет команде, анализ, какие расчёты идут. Критично: оповещение дежурного в чат и звонок. Временно снизить лимит одновременных расчётов для B2B, чтобы освободить ресурсы для операторов. После выноса расчёта в отдельный сервис (I4) — автоматически добавлять воркеры. |
| **CPU Shop API, CRM API** | > 75% в течение 15 мин | > 90% в течение 5 мин | Та же логика. | Предупреждение: тикет. Критично: оповещение дежурного, увеличение ВМ или второй инстанс. |
| **Память API** | > 80% | > 90% или рост без снижения в течение часа | Близко к пределу начинаются долгие паузы сборщика мусора, затем процесс падает. Рост без снижения — признак утечки. | Предупреждение: тикет на анализ. Критично: оповещение дежурного, плановый перезапуск в нерабочее время и разбор утечки. |
| **Соединения БД** | > 70% от `max_connections` | > 85% | При исчерпании соединений новые запросы получают отказ, пользователи видят ошибки 500. Shop DB делят два приложения, и одно может «съесть» соединения другого. | Предупреждение: тикет, проверить «idle in transaction» и утечки соединений. Критично: оповещение дежурного, найти приложение-виновника по ярлыку `application`. |
| **Память БД** | > 80% | > 90% | Данные перестают помещаться в кеш, запросы идут на диск, дашборд MES тормозит. | Предупреждение: тикет, проверить медленные запросы и индексы. Критично: оповещение дежурного, увеличить класс хоста Managed PostgreSQL. |
| **Диск БД, ВМ, RabbitMQ** | Закончится через 14 дней при текущем темпе, или > 75% | Закончится через 3 дня, или > 90% | При полном диске запись останавливается, заказы не создаются. Две недели — достаточно для планового расширения. | Предупреждение: тикет на расширение или архивацию. Критично: оповещение дежурного, увеличить диск. |
| **Очередь RabbitMQ** (п. 2) | Число сообщений в очереди растёт 15 мин подряд | Самое старое сообщение ждёт > 30 мин, или у очереди 0 получателей | Растущая очередь — получатель не успевает. Ноль получателей — сервис отключился, заказы копятся. | Предупреждение: сообщение в чат команды. Критично: оповещение дежурного и звонок. Проверить и перезапустить получателя. |
| **Память RabbitMQ** | > 60% от лимита | Сработал лимит памяти (memory alarm) | При срабатывании лимита RabbitMQ блокирует отправителей, интеграция CRM ↔ MES встаёт целиком. | Предупреждение: тикет. Критично: оповещение дежурного и звонок, разбор очередей-«накопителей». |

| **Очередь расчётов стоимости** | Ожидающих расчётов больше, чем выполняется одновременно, в течение 30 мин | Самая старая заявка ждёт > 1 часа | Средний расчёт — 2–3 мин. Ожидание больше часа значит, что мощности не хватает, и цена для клиента задерживается. | Предупреждение: тикет. Критично: оповещение дежурного, ограничение нагрузки от B2B-партнёров. | **Лимит запросов B2B-партнёра** | Партнёр использует > 80% квоты | Партнёр получает 429 | Партнёр скоро упрётся в ограничение или уже упёрся.
